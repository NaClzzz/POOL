# POOL 简历与面试草稿

## 技术栈（计划）

Next.js、TypeScript、Socket.IO、PostgreSQL、Drizzle、Redis、Better Auth（邮箱＋密码登录）、Zustand、TanStack Query；界面使用 Tailwind CSS 与 shadcn/ui，校验使用 Zod；AI 生成与流式交互使用 Vercel AI SDK。

## 核心亮点与面试展开

### 1. 基于服务端时间轴的多人同步播放

- 问题：用户加入时间、网络耗时和断线重连不同，直接让各端从头播放会产生进度差异。
- 已确定设计：服务端下发起播时间及偏移量，客户端计算当前应播放位置；重连获取房间快照，不逐秒广播进度。支持成员歌单轮播、播放者切歌及其他成员全票切歌。
- 已确定设计：沿用旧项目的服务端播放版本控制；客户端忽略较旧版本状态，服务端校验播放错误上报的版本及曲目，过期上报不推进当前播放。
- 关键边界：客户端断线与服务重启分别处理；重启后播放等待、成员重新上台，不承诺恢复原上台顺序。首版调度时长取网易云服务端歌曲详情，Go/Bilibili 音轨时长仍待后续处理。
- 面试追问：客户端时钟不准怎么办？缓冲导致的偏差如何发现？旧事件和重复切歌如何处理？播放状态由谁决定？
- 验证材料：多浏览器加入、断线恢复和同时切歌测试；记录音频实际进度偏差与恢复耗时，不预写同步精度。

### 2. 音源身份稳定的统一音乐服务

- 问题：不同服务的字段、分页、错误、取流方式不同；更换实现容易影响收藏、播放器和房间业务。
- 已确定设计：业务层经统一服务调用音源适配器，统一搜索、歌曲资料、歌词、播放资源和歌单读取；source + source_id 表示身份，extra 由适配器解释。实现名称不进入条目身份，先接旧网易云 API，Go 服务后续适配。
- 关键边界：歌曲资料与临时播放资源分离；URL 不持久化。Bilibili 分 P 引用需要保留 bvid、cid，作者沿用平台含义，不将 UP 主当作歌手。未接入能力明确返回未支持。
- 已有证据：两源搜索及取流样本、500 首分页、Range 读取和 Edge 解码与定位测试，见 [音乐接口实测](音乐接口实测.md)。测试发现 B 站直链 403、代理流可读，以及资料时长与音轨不一致。
- 面试追问：为什么不建跨平台歌曲实体？代理如何支持 Range？怎样防止代理被当作任意 URL 转发？为什么不直接解析上游页面做业务？

### 3. AI 功能的成本约束与生成生命周期

- 问题：重复生成消耗模型费用，歌曲和聊天输入可能持续增长，多个成员也可能同时触发总结。
- 已确定设计：歌单分析使用完整歌名与随机歌词，喜欢列表最多 500 首，歌词最多 5 首且每首 1,000 字符；房间总结使用最近 500 条播放记录及最多 12,000 字符聊天。请求通过用户、房间额度限制，成功总结供成员共享。
- 关键边界：每房成功生成一次，失败可手动重试，成功后不可主动删除或重新生成；总结生成与查看只检查历史凭证，不区分房主或普通参与者。房间结束满 7 天清理总结、聊天和历史；聊天超过最近 10,000 条可提前淘汰。
- 已确定预算：全站分析与总结共最多 10 个并发，单次模型调用最多 60 秒；分析最多输出 1,200 token，总结最多 2,000 token，截断不视为完整成功，不自动重试。
- 面试追问：两个请求同时生成时怎样避免重复？生成途中断开或进程重启怎么办？额度限制是否等于费用上限？如何评估分析内容是否有依据？
- 验证材料：成功、失败、并发触发、超时与截断、历史凭证删除及过期访问测试；记录实际输入输出 token、费用、首段响应时间和成功率。

### 4. 有容量与权限约束的数据一致性

- 问题：手动收藏、歌单导入可能并发发生；只在前端判断会出现重复收藏或超出 500 首上限。
- 已确定设计：收藏直接保存统一歌曲快照，以 user_id + source + source_id 联合唯一；重复收藏不更新时间。导入按原顺序去重，填满剩余额度，不覆盖已有收藏。
- 需要实现时落实：服务端在同一用户范围内协调容量检查和写入，避免并发绕过上限；数据库约束防重复，容量限制另外处理，不能认为唯一约束同时解决两者。
- 权限边界：每人数据库最多保留 50 条房间历史，记录同时作为总结访问凭证；主动删除或被淘汰即失去访问权，删除个人记录不删除共享总结。
- 面试追问：批量导入部分成功如何反馈？两个导入请求同时发生怎么办？按时间排序相同时如何稳定分页？删除与过期清理如何保持一致？
- 验证材料：接近容量上限时并发导入、重复请求、跨用户访问和历史淘汰测试。

### 5. Redis 缓存、限流与业务状态的职责划分

- 已确定设计：Redis 缓存曲库资料并限流；PostgreSQL 保存持久业务数据；单实例 Socket 服务管理连接和临时房间状态。
- 关键边界：普通缓存失效回源，AI 等高成本接口在限流不可用时拒绝调用；用户额度与音源上游预算分别控制。暂不引入多实例 adapter 或分布式房间状态。
- 面试追问：缓存命中是否计入限流？批量导入如何计算上游预算？缓存和限流共用 Redis 时是否会因淘汰计数而影响预算？窗口边界突发如何处理？
- 验证材料：缓存命中率、实际回源次数、接口耗时分位数和 Redis 不可用时的行为。没有测试数据时不写“显著提升性能”。

### **1. AI 生成全过程管理**

把“调用模型写赏析”做成完整链路：输入整理 → 抽样与截断 → 模型调用 → 流式展示 → 取消与超时 → 结果落库。

值得展开的技术点是：

- 以 token 和费用预算约束输入，字符数作为前置限制。
- 前端取消能够传递到服务端和模型调用，流中断有明确状态。
- 模型密钥、限额和调用记录留在服务端。
- 记录首段响应时间、总耗时、token 消耗和失败类型。

这能体现你理解 AI 功能从界面到模型服务的完整生命周期。流式生成与前端消费已选用 Vercel AI SDK；取消、超时、业务状态恢复与成本控制在实现时验证，不把 SDK 本身提供的能力当作已验证成果。

### **2. 并发安全的 AI 总结生成**

“一房最多一份总结”本身就是有价值的并发问题：

- 多个成员同时触发，如何只启动一个有效生成任务？
- 超时、失败、进程重启后，如何恢复状态并允许重试？
- 模型已返回、数据库写入失败时，如何处理？
- 请求者删除历史或房间已过期时，如何拒绝再次生成和读取？

可以用数据库唯一约束、生成状态和带条件的状态更新落实；不能只靠按钮禁用或进程里的 `Map`。需要区分**防止重复保存**和**防止重复调用模型收费**，两者不是同一个保证。

### **1. 个人跨页面播放与房间音频生命周期管理**

这是很适合突出前端能力的点：

- 个人播放跨页不中断，多个业务页面复用个人音频实例；房间连接和播放器只属于房间页，离开即退房停音并清理订阅、请求和重连。
- 个人播放与房间播放切换时，明确谁拥有播放控制权，避免双重播放。
- 快速切歌时取消旧请求，阻止迟到的播放地址、歌词覆盖新歌曲。
- 正确处理缓冲、自动播放限制、媒体报错和组件卸载。

**亮点表述：**按个人与房间场景划分音频生命周期，实现个人跨页播放和房间页退出清理，通过请求取消和版本校验避免快速切歌或离开页面后的异步竞态。

### **2. 多来源更新下的前端状态一致性**

收藏、房间成员、播放状态可能同时受到 HTTP 响应、Socket 事件和用户操作影响。难点在于：

- 明确服务端缓存、客户端交互状态与音频实例的职责。
- 收藏操作即时反馈，失败时回滚，连续操作时不让旧响应覆盖新状态。
- Socket 重连后以快照校准状态，旧事件不能覆盖新版本。
- 退出登录或切换房间时清理对应缓存和订阅。

**亮点表述：**划分服务端数据与客户端状态，协调请求响应、实时事件和乐观更新，保证切房、重连及连续操作后的界面一致性。

### **3. 支持定位播放的鉴权音频代理**

这项前后端都有深度，且你的 B 站实测已经证明存在需求：

- 前端需要跳转到房间当前进度。
- 服务端正确处理 `Range`、`206`、`Content-Range` 和媒体类型。
- 流式转发，避免整首音频读入内存；客户端断开时停止上游传输。
- 校验用户和平台条目，代理目标由适配器解析。

**亮点表述：**实现支持 Range 的鉴权音频代理，处理平台直链访问限制，并支持房间加入、重连后的定位播放。

### **4. 并发安全的批量歌单导入**

将“导入歌单”展开为完整业务：

- 分页读取、去重、批量写入，导入至剩余容量。
- 手动收藏和导入并发发生时，仍保证不重复、不超过 500 首。
- 前端展示导入状态与结果，区分新增、重复和超额。
- 明确重复提交及部分失败的处理规则。

这里能讲清楚事务、唯一约束、并发控制和用户反馈，而不仅是 CRUD。

### **5. 歌曲列表与播放进度的渲染性能**

重点是**高频进度更新不拖着整页重渲染**：把进度展示与歌曲列表隔离，减少无关订阅。长列表是否需要虚拟化，则根据实际测量决定。

可以记录组件渲染次数、交互耗时，再说明优化效果；500 首本身不足以支撑“大数据量高性能”这种表述。

## 简历表述草案（完成后按实际能力选 3～4 条）

- 基于服务端起播时间轴与房间快照实现多人轮流听歌及断线恢复，减少逐秒进度广播；通过多端测试验证同步偏差和恢复耗时。
- 设计统一音乐服务及音源适配层，隔离资料、分页、歌词与取流差异，使用稳定的平台条目身份保存收藏；支持鉴权代理与 Range 取流。
- 实现歌单链接批量导入与收藏去重，通过数据库唯一约束和服务端并发控制保证收藏容量及重复请求的一致性。
- 为 AI 歌单分析与房间总结设计输入预算、调用额度和成功后锁定机制，结合成员权限及 7 天保留规则控制调用成本与数据生命周期。

仅接通一种音源时描述“统一接口与网易云适配”，第二种接通并验证后再写“多音源”。房间总结未实现时从简历中移除，或单列为规划，不混入已完成功能。

## 可讨论的新增亮点（尚未纳入开发范围）

| 建议 | 解决的问题 | 可验证成果 | 优先级 |
| --- | --- | --- | --- |
| 多客户端自动化验证与同步指标 | 同步、重连和并发行为难以靠手测证明 | 实际进度差的 P50/P95、恢复耗时、重复切歌次数及测试环境 | 高 |
| 生成任务状态与数据库幂等控制 | 多人触发、失败重试、进程中断可能重复收费或永久卡住 | 一房一份成功总结、重复请求共享状态、失败可恢复 | 总结开发时优先 |
| 相同曲库请求合并与缓存效果观测 | 多成员同时请求同一歌词或资料造成重复回源 | 同一进程中相同请求只回源一次，记录命中率和调用次数 | 中 |
| AI 结果依据与小规模评估集 | 有文本输出不等于分析有依据 | 对少歌词、混合语言、无效标题等样本评估编造内容与推荐越界 | 中 |

优先完善现有功能的正确性、可观测性和测试证据，再讨论增加新功能。毫秒级精度、高并发容量、费用下降比例等指标必须实测；测试浏览器数量、网络条件、样本及统计口径一并记录。

## 基础工程实践

Axios 请求封装、表单校验、代码检查、组件拆分和容器部署可以放在工程实践中，不单独作为主要亮点。面试时说明它们解决的具体重复逻辑或错误处理问题，避免只罗列库名。Zustand 与 TanStack Query 的数据职责需在实现时落实，同一份服务端数据不维护两套无同步规则的副本。
