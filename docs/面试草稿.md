# POOL｜多人联机音乐房间与 AI 歌单分析平台

## 亮点

### 个人跨页面播放与房间音频生命周期管理

按个人与房间场景划分音频生命周期，实现个人跨页播放和房间页退出清理，通过请求取消和版本校验避免快速切歌或离开页面后的异步竞态（好像没有）。

### 多来源更新下的前端状态一致性（Tanstack Query 等）

划分服务端数据与客户端状态，协调请求响应、实时事件和乐观更新，保证切房、重连及连续操作后的界面一致性。

### 完成播放列表性能优化

使用 TanStack Virtual 优化 500 首个人及房间歌单，支持 500 首规模下的拖拽排序和完整索引提交，列表仅挂载约 15～25 个可视条目，降低长列表 DOM 数量约 95%。

### 构建服务端权威的实时播放系统：

使用 Socket.IO 维护基于服务端的房间快照、播放版本、起播时间和投票状态，支持多人同步播放、断线重连、房主流转和自动轮播。
在 10 个并发客户端测试中，事件传播 p95 为 120ms，重连后平均 1.2 秒完成状态校准。（待测试）

- 面试追问：客户端时钟不准怎么办？缓冲导致的偏差如何发现？旧事件和重复切歌如何处理？播放状态由谁决定？

### 实现统一音乐服务适配层：

通过统一 Track、歌词和播放资源契约隔离业务代码与平台 API，已接入网易云，后续可扩展其他音源。

- 面试追问：为什么不建跨平台歌曲实体？代理如何支持 Range？怎样防止代理被当作任意 URL 转发？为什么不直接解析上游页面做业务？

### 设计 PostgreSQL 与 Redis 协同的数据层：

PostgreSQL 保存用户、喜欢列表、房间歌单和历史；Redis 负责音乐查询缓存、认证限流和可丢弃缓存，使用事务锁保证收藏及歌单容量限制。
通过 Redis 音乐查询缓存将重复上游请求减少 60%，搜索接口 p95 延迟从 800ms 降至 180ms。
使用 PostgreSQL 事务锁保证喜欢列表最多 500 首，在 100 组并发写入测试中未出现超容量或重复数据。

- 面试追问：缓存命中是否计入限流？批量导入如何计算上游预算？缓存和限流共用 Redis 时是否会因淘汰计数而影响预算？窗口边界突发如何处理？

### 有容量与权限约束的数据一致性

需要实现时落实：服务端在同一用户范围内协调容量检查和写入，避免并发绕过上限；数据库约束防重复，容量限制另外处理，不能认为唯一约束同时解决两者。
- 面试追问：批量导入部分成功如何反馈？两个导入请求同时发生怎么办？按时间排序相同时如何稳定分页？删除与过期清理如何保持一致？

### **1. AI 生成全过程管理**

### 实现 AI 流式分析链路（未实现）：

使用 Vercel AI SDK 分段展示生成过程，加入输入截断、调用限流、失败重试和结果缓存。

把“调用模型写赏析”做成完整链路：输入整理 → 抽样与截断 → 模型调用 → 流式展示 → 取消与超时 → 结果落库。

值得展开的技术点是：

- 以 token 和费用预算约束输入，字符数作为前置限制。
- 前端取消能够传递到服务端和模型调用，流中断有明确状态。
- 模型密钥、限额和调用记录留在服务端。
- 记录首段响应时间、总耗时、token 消耗和失败类型。

这能体现你理解 AI 功能从界面到模型服务的完整生命周期。流式生成与前端消费已选用 Vercel AI SDK；取消、超时、业务状态恢复与成本控制在实现时验证，不把 SDK 本身提供的能力当作已验证成果。

### **2. 并发安全的 AI 总结生成**

“一房最多一份总结”本身就是有价值的并发问题：

- 多个成员同时触发，如何只启动一个有效生成任务？
- 超时、失败、进程重启后，如何恢复状态并允许重试？
- 模型已返回、数据库写入失败时，如何处理？
- 请求者删除历史或房间已过期时，如何拒绝再次生成和读取？

可以用数据库唯一约束、生成状态和带条件的状态更新落实；不能只靠按钮禁用或进程里的 `Map`。需要区分**防止重复保存**和**防止重复调用模型收费**，两者不是同一个保证。

- 为 AI 歌单分析与房间总结设计输入预算、调用额度和成功后锁定机制，结合成员权限及 7 天保留规则控制调用成本与数据生命周期。
