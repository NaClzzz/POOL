## 4. 下一步建议范围：基础后端与账号系统

目标是先建立“数据库可迁移 → 真实注册登录 → 服务端会话 → 受保护页面与接口 → 退出失效”的最小完整链路，不一次替换所有模拟业务。以下为接入准备，尚未实施。

1. **基础后端**：沿用 PostgreSQL、Drizzle 与 Better Auth 选型；建立服务端目录、环境配置、数据库连接、迁移和可复用的请求身份读取入口。认证核心不依赖 Next.js 专用请求上下文，便于后续 Socket 服务复用。先建立认证所需 schema，不要求同时落地全部房间与 AI 表。
2. **真实账号**：区分邮箱密码注册、登录、读取当前会话和退出；用户、密码凭据及会话交由 Better Auth 管理，不另造一套认证表或浏览器令牌存储。表名与字段根据实施时选定版本生成并核对。
3. **访问边界**：未登录不能访问业务页面；服务端业务入口独立校验会话，不能只依赖 AppShell 的客户端重定向。过期会话和退出后的请求应被拒绝，不信任浏览器提交的 userId。
4. **响应与错误**：普通业务 JSON 使用服务端设计的 ApiResult、真实 HTTP 状态码和 requestId；`/api/auth/*` 保留认证库原生协议。添加一个最小受保护业务入口来验证服务端身份与未登录响应，不以 mock 的 requireUser 代替鉴权。
5. **前端接入**：保留登录注册和设置页外观，统一会话数据来源；处理初始化、提交中、注册失败、登录失败、会话失效及退出。继续清理私有 Query 缓存、个人音频与房间投影，避免换号后残留前一用户内容。
6. **验证与运行说明**：补环境变量示例、数据库准备及迁移步骤；验证空库初始化、重复执行迁移、注册登录、刷新恢复、退出失效和账号隔离。开发代理与云服务器同域部署的配置需分别可复现。

### 接入前需要落实的事项

- **身份过渡**：其他业务继续 mock 时，先在模拟服务边界提供真实用户 ID 的适配，统一模拟资料的归属；不能出现页面显示真实用户、业务仍读取旧演示账号的情况。不默认迁移浏览器里的演示资料到真实账号。
- **协议差异**：现有 mock 服务直接返回解包后的数据，完整分页、服务端房间歌单 itemId 和播放 DTO 尚未落地。正式接入时逐个对齐，不仅将函数体改成请求地址。
- **认证参数**：实施前细化会话期限、是否保持登录、邮箱验证与密码找回范围、注册后行为及登录限流方案；未接入邮件服务时不显示可用的验证／找回能力。具体值维护到服务端设计。
- **演示隔离**：真实认证模式下停用“使用演示账号”等身份捷径；保留的 mock 业务和演示控制要明确范围，不能让重置演示数据变成生产数据删除入口。
- **房间路由**：AppShell 当前通过 `/rooms/pool-` 前缀识别房间页，依赖演示房间号。真实房间接入前应改为按路由结构判断，避免新的 roomCode 破坏房间布局。
- **依赖与部署**：当前尚未安装 Drizzle、Better Auth、数据库驱动和 Redis 客户端，也没有真实服务配置；按实施时文档和版本接入。Redis 仍只负责缓存及限流，不承担登录会话或房间状态的默认存储职责。

## 5. 下一步完成的判断标准

- 从空数据库可按文档完成迁移，真实账号与会话可查询，浏览器不保存密码或伪造身份凭据。
- 注册、错误密码、重复邮箱、登录、刷新恢复会话、退出和失效会话均有明确结果；退出后旧会话不能继续调用受保护接口。
- 直接访问受保护页面及绕过页面请求业务接口都会验证服务端身份；客户端修改 userId 不能切换操作者。
- 两个真实账号的前端缓存、模拟业务归属及播放状态相互隔离；演示资料不会自动写入真实账号数据库。
- 所有仍由 mock 驱动的搜索、房间和 AI 能力继续明确标识；真实账号完成不等于真实多人房间、音乐服务或模型接入完成。
- 必要的自动检查及真实数据库／会话集成验证通过，设计文档、环境示例和运行步骤与代码一致。

本次只补充阶段交付记录与接入准备文档，不创建后端代码、不安装依赖、不启动服务。下一阶段具体开发范围由后续任务确定。
